A Phoenix router is a pile of macros that build a data model for verified routes to check against.

Why can't we do that for pub/sub?

Verified routes works because of the Phoenix router module. For our purposes, the router is a whole bunch of macros that build up a data model for a verified route to validate against. Why can't we do the same thing for pub/sub?

The manifest

defmodule MyApp.Topics do
  use VerifiedPubSub.Manifest, pubsub: MyApp.PubSub

  topic :campaigns, "accounts:%{account_id}:campaigns" do
    message :created do
      field :id, :string
      field :name, :string, required: false
    end

    message :updated do
      field :id, :string
    end

    message :deleted do
      field :id, :string
    end
  end
end
Here we're defining a what I'm calling a manifest module. Think shipping manifest. The DSL is currently implemented in Spark, so if you've ever looked at Ash code, this is probably pretty familiar. First, we have a topic. This is a topic about campaigns. The shape of the topic is "accounts:%{account_id}:campaigns". So, this will be messages about campaigns for a specific account. Then we have the messages we expect to publish on this topic. We have some simple create, update, delete messages that we'll publish along with the expected shape of those messages. When creating a campaign, we expect the payload to have an id and optionally a name. We see that updated and deleted only expect ids.

One place that says what is on the wire.

  • What can be broadcast and received on this topic
  • What each of those messages looks like

Here we send minimal information and let subscribers load from the DB. You could just as easily send everything. Either way, it's explicit.

This immediately makes clear to us the what messages we can expect to broadcast and receive on this topic. It makes clear what those messages would like. In this case, we're sending over minimal information. If the subscriber wants more info about the campaign, they'll have to load it from the DB. Alternatively, you could define a pub/sub topic that sends a lot of information over the wire so subscribers don't have to load it from the DB. Either way, this is making the usage very clear.

Broadcast

defmodule MyApp.Campaigns do
  use VerifiedPubSub, manifest: MyApp.Topics

  def create(attrs) do
    # ...
    broadcast(:campaigns, %{account_id: "7"}, :created, %{id: "c1"})
  end
end

broadcast/4 returns :ok | {:error, term}. broadcast!/4 raises instead.

Now, let's look at the usage of this. I tried to keep an API that looks pretty similar to the Phoenix pub/sub that you're used to. In the module you're broadcasting from, you need to use VerifiedPubsub and give the manifest module you're using. We're going to broadcast a campaign created message. You can see that we're broadcasting on the campaign topic. That topic is parameterized with an account_id. Then we have the :created atom and the payload itself, which is just a map with a single id key. Name was optional in our manifest, so that is fine.

Subscribe

defmodule MyApp.Worker do
  use GenServer
  use VerifiedPubSub.Subscriber, manifest: MyApp.Topics

  def init(_arg) do
    :ok = subscribe(:campaigns, %{account_id: "7"})
    {:ok, %{}}
  end
end
Subcribing to this will feel pretty similar to Phoenix pub/sub as well. We use VerifiedPubsub again and pass our manifest. We subscribe to it like this.

Handling messages

handle_message :campaigns, :created, payload, state do
  # ...
end

handle_message :campaigns,
               :updated,
               %Message{payload: %{id: id}},
               state do
  # ...
end
To handle messages, we're back to a macro. We define handle_message. It handles messages on the campaigns topic. We handle both the :created and :updated messages here. We pattern match the id out of the message and then handle it like normal in our process. It's just a message sent to a process at that point.

Now the interesting part.

handle_message :campaigns, :invalid, payload, state do
  send(state.owner, {:created, payload})
  {:noreply, state}
end
** (CompileError) lib/my_app/worker.ex:12: MyApp.Worker handles messages that MyApp.Topics does not declare:

  * :campaigns, :invalid — MyApp.Topics declares [:created, :updated, :deleted] on :campaigns

Fix the event name, or declare it in the manifest.
Where it gets more interesting is the compile time support we have. Change the message name to :invalid and it doesn't compile.

Events you don't care about must be ignored on purpose.

ignore_message :campaigns, :deleted
And circling all the way back to the original debate with my co-worker, what if the topic defines messages we don't care about in this process? We must explicitly ignore them.

Otherwise it doesn't compile.

** (CompileError) lib/my_app/worker.ex:12: MyApp.Worker subscribes to topics with events it does not account for:

  * :campaigns, :deleted

Add a `handle_message` clause for each, or dismiss it explicitly:

    ignore_message :campaigns, :deleted

Manifest: MyApp.Topics

Add an event to a topic, and every subscriber has to decide what to do about it — at compile time.

If we don't, we get a compilation error like this. As we add messages to our topics, we must explicitly decide how to handle it at compile time.
