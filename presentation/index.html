Pub/Sub Philosophy

A couple of years ago one of my co-workers and I were having a debate over how our system should handle pub/sub events. My position was that a process that receives unexpected pub/sub events on a topic should not crash. His opinion was that it should.

🫠

This took me down a rabbit hole of evaluating our pub/sub code. Frankly, it was a mess. There had never been a coherent philosophy for how it should be used or organized. There was no way to easily see the pub/sub topics and events our system used. Modules called subscribe and broadcast directly.

The deeper I went, the worse it got. This wasn't surprising. We knew it was bad, but it was still disheartening. The breaking point for me was seeing the same event broadcast from three different modules and none of them agreed on what the shape of the payload should be.

Verified Routes

It would have been really great if we could have some compile-time verification of this stuff. Verified routes was in the realm of what I wanted. But, I'm lazy. I talked to some people about it, but didn't do anything. They were usually intrigued, but I have kids and hobbies. This was metaprogramming work well beyond my current skill set.

Verified PubSub

But we have LLMs now. Let's talk about verified pub/sub.

🚫 Do not use any of this in production 🚫

But before that. You should not use anything I'm about to show you in production yet! I haven't even used it on any projects yet. This is purely a proof of concept at the moment. I'll be talking about this at ExMex in November. It will hopefully be much more fleshed out by then.

Verified routes works because of the Phoenix router module. For our purposes, the router is a whole bunch of macros that build up a data model for a verified route to validate against. Why can't we do the same thing for pub/sub?

Manifests

defmodule MyApp.Topics do
  use VerifiedPubSub.Manifest, pubsub: MyApp.PubSub

  topic :campaigns, "accounts:%{account_id}:campaigns" do
    message :created do
      field :id, :string
      field :name, :string, required: false
    end

    message :updated do
      field :id, :string
    end

    message :deleted do
      field :id, :string
    end
  end
end

This is a manifest module. Think shipping manifest. It's a lot of macros using Spark.

First, the topic. This one is about campaigns, and its shape is "accounts:%{account_id}:campaigns". So, messages about campaigns for a specific account.

Then the messages we expect to publish on it. Created carries an id and optionally a name. Updated and deleted only carry ids. That is the whole contract, in one place: what we can broadcast on this topic, and what each message looks like.

Broadcast

defmodule MyApp.Campaigns do
  use VerifiedPubSub, manifest: MyApp.Topics

  def create(attrs) do
    # ...
    broadcast(:campaigns, %{account_id: "7"}, :created, %{id: "c1"})
  end
end
I tried to keep an API that looks pretty similar to the Phoenix pub/sub that you're used to. In the module you're broadcasting from, you need to use VerifiedPubsub and give the manifest module you're using. We're going to broadcast a campaign created message. You can see that we're broadcasting on the campaign topic. That topic is parameterized with an account_id. Then we have the :created atom and the payload itself, which is just a map with a single id key. Name was optional in our manifest, so that is fine.

Subscribe

defmodule MyApp.Worker do
  use GenServer
  use VerifiedPubSub.Subscriber, manifest: MyApp.Topics

  def init(_arg) do
    :ok = subscribe(:campaigns, %{account_id: "7"})
    {:ok, %{}}
  end
end
Subscribing to this will feel pretty similar to Phoenix pub/sub as well. We use VerifiedPubsub again and pass our manifest. We subscribe to it like this.

Handling messages

handle_message :campaigns, :created, payload, state do
  # ...
end

handle_message :campaigns,
               :updated,
               %Message{payload: %{id: id}},
               state do
  # ...
end
In our subscribing process, we define handle_message. This one handles messages on the campaigns topic. We handle both the :created and :updated messages here. We pattern match the id out of the message and then handle it like normal in our process. It's just a message sent to a process at that point.

Invalid Messages

handle_message :campaigns, :invalid, payload, state do
  send(state.owner, {:created, payload})
  {:noreply, state}
end
** (CompileError) lib/my_app/worker.ex:12: MyApp.Worker handles messages that MyApp.Topics does not declare:

  * :campaigns, :invalid — MyApp.Topics declares [:created, :updated, :deleted] on :campaigns

Fix the event name, or declare it in the manifest.
Where it gets more interesting is the compile time support we have. Change the message name to :invalid and it doesn't compile.

Ignoring Messages

ignore_message :campaigns, :deleted
And circling all the way back to the original debate with my co-worker, what if the topic defines messages we don't care about in this process? We must explicitly ignore them.

Handle or Ignore 'Em All

** (CompileError) lib/my_app/worker.ex:12: MyApp.Worker subscribes to topics with events it does not account for:

  * :campaigns, :deleted

Add a `handle_message` clause for each, or dismiss it explicitly:

    ignore_message :campaigns, :deleted

Manifest: MyApp.Topics
If we don't, we get a compilation error like this. As we add messages to our topics, we must explicitly decide how to handle it at compile time.
